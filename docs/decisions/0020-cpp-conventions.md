# ADR-0020: C++ conventions

- **Status:** Accepted
- **Date:** 2026-11-12

## Context
`.clang-format` fixes layout, but not the choices that affect the ABI, determinism and running inside other programs' processes (ADR-0015). These are cheap to set now and expensive to change later.

## Decision

**Language & compiler**
* C++20, MSVC, `/W4 /permissive- /utf-8`; warnings as errors in CI.
* **`/fp:precise`, never `/fp:fast`** (or any fast-math): fast-math breaks determinism (ADR-0007).
* `float` (32-bit) throughout the simulation; no double precision (ADR-0012).

**Errors & exceptions**
* DragDoll code never throws. Errors are values: `DdResult` enum at the C ABI, `dragdoll::Result<T>` (or `std::expected`) internally.
* Compiled with `/EHsc` so the standard library stays well-defined, but **every C ABI function is `noexcept` and catches everything** at the boundary, converting it to `DD_ERROR_INTERNAL`. No exception ever crosses into a host.
* Human-readable detail: `dragdoll_last_error_message()` (thread-local).
* `DD_ASSERT` in debug builds; release builds validate inputs at the C API boundary and fail with a result code, never crash.

**Memory & ownership**
* RAII everywhere; no naked `new`/`delete` (Jolt's `Ref<>`/`RefConst<>` for Jolt objects, `std::unique_ptr` for ours).
* All allocations go through Jolt's allocator hooks or DragDoll's allocator, so per-world memory is accounted (ADR-0015).
* C ABI: opaque handles with explicit `dragdoll_*_create` / `dragdoll_*_destroy` pairs. **Output buffers are caller-owned** (the host allocates pose arrays; DragDoll fills them). DragDoll never returns memory the host must free.
* No global objects with non-trivial constructors or destructors (DLL load/unload order inside games is unpredictable). Explicit `dragdoll_init` / `dragdoll_shutdown`.

**Threads**
* A world is not thread-safe: one thread drives a world at a time. Internal parallelism uses Jolt's job system with a host-configurable worker count.
* DragDoll never calls host callbacks from worker threads; callbacks (logging, events) are delivered on the calling thread during `dragdoll_world_step`.

**RTTI & logging**
* No `dynamic_cast` / `typeid` in core (Jolt has its own RTTI where needed). RTTI may stay enabled for tests/tools.
* No `printf`/console output from core: logging goes through a host-installable callback with levels.

**Naming**
* Files: `snake_case.hpp` / `.cpp`; `#pragma once`.
* Namespaces: `dragdoll`, `dragdoll::detail` (lowercase).
* Types, enums, enum values: `PascalCase`. Functions, methods, variables: `camelCase`. Members: `m` prefix (`mVelocity`, matching Jolt). Constants: `kPascalCase`.
* C ABI: functions `dragdoll_snake_case`, types `DdPascalCase`, macros/enum constants `DD_UPPER_CASE`.

## Consequences
* Hosts (SA plugin, engines, other languages) can rely on: no exceptions, no hidden allocations they must free, no surprise threads calling into them.
* Slightly more boilerplate at the C boundary (try/catch wrappers, result codes) — generated by one macro.

## Sources
Jolt Physics coding style; MSVC documentation (`/fp`, `/EH`); common C ABI library practice (e.g. SQLite, Vulkan).
